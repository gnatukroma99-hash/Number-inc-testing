# AGENTS.md — правила работы над проектом «ЧИСЛО»

Файл правил для агента (меня). **Читать в начале каждой сессии вместе с `CONTEXT.md`.**
При конфликте с сообщением пользователя в чате — **побеждает чат, немедленно и без обсуждения**.

---

## 0. Главный принцип

Проект должен **масштабироваться бесконечно**: новые ярусы, механики, барьеры, валюты добавляются
**данными, а не переписыванием кода**. Любое решение, которое упирается в «а вот тут придётся переделать всё», — неверное.

---

## 1. Рабочий процесс

### 1.1 Дробление задачи
1. Любую задачу **разбивать на части** письменно, до кода.
2. Показать список частей пользователю, чтобы он мог переставить приоритеты.
3. **Делать за раз ровно одну часть.** Не «заодно прикрутить ещё пять вещей».
4. Каждая часть должна быть самостоятельно проверяема.

### 1.2 После каждой части — отчёт
Строго в этом порядке:
1. **Что сделано** — короткими пунктами, с путями файлов.
2. **Как проверить** — что нажать / что должно быть на экране.
3. **Известные ограничения** — что пока не работает.
4. **Вопросы / варианты** — 2–4 варианта следующего шага с моей рекомендацией.

Без отчёта следующую часть не начинать.

### 1.3 Приоритет указаний
Пользователь говорит в чате «делай так» → делаю так сразу, даже если противоречит ТЗ.
После этого **обновляю ТЗ / AGENTS / CONTEXT**, чтобы документы не расходились с кодом.
Не спорю дважды: сомнение высказал один раз → дальше исполняю.

### 1.4 Контекст между сессиями (важно)
- `CONTEXT.md` — слепок состояния проекта и договорённостей. **Начало сессии: прочитать.**
- **Конец каждой сессии / крупной части: обновить `CONTEXT.md`** — статус, решения, открытые вопросы, что дальше.
- `docs/CHANGELOG.md` — что именно вошло в версию.

### 1.4.1 Баланс после каждой обновы (жёсткое правило)

1. После **каждой** порции механик/апгрейдов запускать `node tools/bench.js 1 300`
   (реальный код, включая P1) и `node tools/sim.js 160 900`, фиксировать время до **1e308**.
2. На **первом прогоне** (без перерождений) время до 1e308 **не должно быть меньше 60 минут**,
   даже когда механик станет больше. Ориентир — 75–85 минут.
3. Если новый апгрейд/механика **не даёт заметного буста** — усилить или убрать.
   Если даёт слишком много и ломает время — усилить невидимый софткап (`knee/span/power`) и цены.
4. Результат замера записывать в `CONTEXT.md` и `docs/CHANGELOG.md` (строка «1e308 за N мин»).

### 1.5 Тестирование
- Git for Windows + Node установлены → **агент сам проверяет** `node --check` и `node tools/sim.js`,
  прогоняет логику в Node-песочнице (без DOM) и сообщает реальные цифры.
- **С сессии №6 у агента есть DOM (jsdom):** `node tools/domtest.js` поднимает настоящий
  `index.html`, все скрипты, игровой цикл, кликает по доскам/кнопкам/дереву/перерождению,
  300 раз гоняет `render()` и ищет `Infinity/NaN/undefined` в тексте.
  Перед первым прогоном в новой копии: `npm i` (ставит только jsdom, `node_modules/` в .gitignore).
- `node tools/checkall.js` — синтаксис всех `.js`, совпадение `VERSION` ↔ `G.VERSION` ↔ `?v=`,
  все `<script src>` существуют, все файлы механик подключены, нет ESM и `^` в формулах.
- **Скриншоты в настоящем браузере:** `node tools/shot.js` (headless Chrome/Edge через
  `puppeteer-core`) кладёт PNG в `tools/shots/` — агент смотрит вёрстку глазами сам.
  Перед первым прогоном: `npm i` (jsdom + puppeteer-core; `node_modules/` в .gitignore).
- **Юзер всё равно проверяет вкус и ощущения** — но агент ловит ошибки UI и грубые косяки сам.
- Проверять: консольные ошибки, миграцию старого сейва, `file://`, отсутствие `Infinity`.
- Порядок после каждой части: `node tools/checkall.js` → `node tools/domtest.js` →
  `node tools/bench.js 1 300` → `node tools/sim.js 160 900` → цифры в отчёт.

## 2. Правила дизайна игры

1. **Число всегда растёт** (магазин может временно уменьшить его на цену покупки — это осознанная трата). Никаких абсолютных потолков. Видимый софткап/локкап — временный, снимается навсегда.
   Невидимый софткап (`content.hiddenSoftcap`) — не потолок, а плавное замедление; он регулирует темп.
2. **Главное число всегда на экране** (позиция настраивается). По нему не кликают; тратить его можно
   только через магазин `shop` (цена в цифрах `costD`, ниже 2 цифр не опускается) — изменение v0.2.0.
3. **Новая механика не плодит вкладки без автоматизации.** Если доска не автоматизируется
   быстро (авто-апгрейд/идл), её нельзя добавлять отдельной вкладкой — лучше объединить
   с существующей доской (пример: `analysis` = три эффекта в одной вкладке).
4. **Остальные механики живут на своих «досках»**: сначала ручные, потом автоматизируются апгрейдами → идл.
   «Ручное → автоматика» — основная фантазия прогресса.
5. **Мета-прогресс не сбрасывается.** Всё, что бафает *во время раунда*, — сбрасывается (`scope: run`).
5.1. **Покупки массовые** (×1/×10/×100/MAX) — как в популярных инкременталках; новый магазин
   обязан работать через `upgrades.plan()/buyBulk()`, а не своим циклом.
6. **Тон:** мемно, но сдержанно. **Мат нельзя.** Культовые цитаты — только в ачивках.
   Формулы всегда настоящие.
7. **Каждая механика обязана синергировать** с ростом числа. Механика, не влияющая на `D`, — украшение или удаляется.
7.1. **Звук — только синтезом (WebAudio), без файлов и запросов**, включается/выключается в настройках
   (`settings.sound`), подписывается на `G.bus`, а не вызывается из UI.
8. **Итерации по фидбеку:** выдаю версию → пользователь тестирует → правим баланс/баги → следующая порция механик.
   Не пытаться сделать всё сразу.

## 3. Правила кода

1. **Ни одного магического числа в логике.** Все константы — в `game/src/content/`.
2. **Всё декларативно.** Ресурсы, апгрейды, ярусы, барьеры, доски — данные + строки-формулы.
3. **Формулы — строками** (`"log10(N) ** 1.5 * lvl"`), считаются общим парсером `core/formula.js`.
   ⚠️ Степень — только `**` или `pow(a,b)`. Знак `^` в JS — это XOR, использовать нельзя.
4. **Один файл = одна ответственность.** Больше ~250 строк — повод разбить.
5. **BigNum везде.** Арифметика над `N` — только через `G.BN`.
6. **Сейв только через `state.serialize()`** с версией и миграциями. `JSON.stringify(state)` напрямую запрещён.
7. **Никаких сетевых запросов.** Игра работает из `file://`.
8. **Классические скрипты, не ESM.** Из `file://` ESM блокируется CORS. Каждый файл — IIFE в `window.G`.
9. **Системы не знают про UI.** Общение — через `G.bus`.
10. **Механика = папка** `game/src/mechanics/<id>/` (копия `_template/`). Добавление механики
    не требует правок в других папках — это критерий масштабируемости.
11. **`scope` в каждой декларации** → универсальный сброс, без ручных списков.

## 4. Как строить сложные системы (анализ референсов)

Референсы для **архитектуры кода**, а не для копирования механик:

- **Shark Incremental** — https://github.com/MrRedShark77/shark-incremental
- **Really Grass Cutting Incremental** — https://github.com/MrRedShark77/Really-Grass-Cutting-Incremental
- **Celestial Incremental** — https://github.com/Icecreamdudes/celestial_incremental (движок The Modding Tree)

### 4.1 Что у них реально устроено так (и что мы перенимаем)

| Приём из референсов | Как применяем у нас |
|---|---|
| **Отдельная «нотация»** (у RGCI — `break_eternity.js`) — библиотека чисел, поддерживающая тетрацию/башни, чтобы `10^^100` не превращалось в `Infinity` | `core/bignum.js` уже отдельный; при Ярусе 3 расширить до башен `{m, e, layer}` (или подключить break_eternity как классический скрипт) |
| **`formulas.js` отдельно от `main.js`** — все формулы в одном месте, движок их только вызывает | `core/formula.js` + формулы строками в данных |
| **Слой (layer) как объект с контрактом** (The Modding Tree): `resource`, `gainMult()`, `prestige()`, `upgrades[]`, `milestones[]`, `challenges[]`, `buyables[]`, `clickables[]`, `tabFormat`, `hotkeys` | Наш контракт механики + будущие `buyables`/`milestones`/`challenges` как отдельные системы, читающие данные |
| **Единое хранилище `player[layerId]`** — у каждого слоя своё поддерево состояния, сейв собирается обходом | `state.mech[<id>]` — приватные данные механики; `state.serialize()` собирает их обходом |
| **Пайплайн эффектов** — множители не «вшиты», а собираются из всех источников и перемножаются | `growth.M()` перемножает `mult()` всех механик; новые источники подключаются, ничего не переписывая |
| **Цепочка софткапов** — `softcap(x, start, power)` накладывается поверх значения, несколько раз | `growth.barrierFactor()` — список барьеров из данных, каждый режет свой диапазон |
| **Покупки как генераторы** — `cost(level)` / `bulk buy` / `max buy` / `autobuy` в одном месте | `systems/upgrades.js`: `cost`, `canBuy`, `buy(times)`; авто-уровни `auto1..auto3` в плане |
| **Милстоуны по порогам** — массив `{req, effect}`, движок просто ищет пройденные | планируемая система `milestones` в данных |
| **Челленджи как модификатор состояния** — при активном челлендже функции возвращают урезанные значения (`inChallenge('x')`) | `challenges.js` будет заворачивать `growth.M/dt` в модификаторы, а не ветвить код |
| **Кэш и «грязные» флаги** — тяжёлые расчёты пересчитываются только при изменении (иначе тик на 1000 слоёв умирает) | сейчас пересчитываем каждый тик (мало механик), но при росте — `unit: cache` с инвалидацией по событию покупки |
| **Оффлайн через закрытую формулу**, а не пошагово | `save.applyOffline()` — `log10`-приращение за один шаг, без цикла |
| **Формат числа как отдельный модуль с настройками** | `core/format.js` + формат в настройках |
| **UI строится один раз, потом только патчится** (иначе 30 fps недостижимы) | контракт доски `mount() -> {update(state)}` |

### 4.2 Правила для будущих сложных функций

1. **Никаких «умных» функций на 200 строк.** Сложная логика = композиция 4–6 маленьких функций, каждая тестируема.
2. **Функция не знает, кто её вызвал.** Всё через аргументы (`state`, `dt`, `lvl`), без глобальных тайников.
3. **Сначала контракт, потом код.** Перед новым слоем/системой — расписать в `ARCHITECTURE.md`: что входит, что выходит, кто читает.
4. **Один источник правды.** `N` живёт в `state.N`; производные (`D`, `M`, `ΔT`) считаются, а не хранятся (кроме кэша).
5. **Связи только через реестр и события.** Механика A не вызывает механику B напрямую; B сам подписывается/сама отдаёт `mult()`.
6. **Всё, что можно вынести в данные — выносить.** Если для новой механики нужен `if (id === 'x')` в движке — это ошибка дизайна.
7. **Производительность с самого начала:** тик ≤ 2 мс, без создания объектов/массивов в горячем цикле, без `JSON` в тике.
8. **Обратная совместимость сейва** обязательна: новые поля — с дефолтами, старые сейвы не ломаются.
9. **Перед добавлением механики спросить: как она усиливает существующие?** Цепочки синергии важнее количества.

## 5.1 Версионирование и публикация (GitHub)

Репозиторий — единственный источник правды о проекте. Правила:

1. **Каждая законченная часть → новая версия.** Не копить 10 фич без публикации.
2. Порядок выпуска версии:
   `VERSION` (бамп) → `G.VERSION` в `state.js` → `?v=<версия>` у всех скриптов в `index.html`
   (иначе GitHub Pages отдаст старый JS из кэша) → `docs/CHANGELOG.md` → `CONTEXT.md` →
   напомнить пользователю запустить `PUSH_VERSION.bat`.
3. Схема версий: `0.x.0` — новая механика/ярус, `0.x.y` — баланс/баги/косметика, `1.0.0` — Ярус 1 стабилен.
4. **Никогда не коммитить секреты.** Токен GitHub живёт только в `localStorage` браузера; в репозиторий не попадает.
5. Публикация — через `PUBLISH_SETUP.bat` (первый раз) и `PUSH_VERSION.bat` (каждый раз). `GIT_STATUS.bat` — посмотреть состояние.
6. Git-команды агент не запускает (нет shell) → **всегда сообщать пользователю**, что нужно нажать `.bat`.
7. Если пользователь установит **Git for Windows** — у агента появится `bash` и он сможет сам проверять код и состояние репозитория. Напоминать об этом при любой отладке.

## 6. Чего не делать

- Не использовать мат и грубости.
- Не добавлять механики с кликом по **главному числу**.
- Не хардкодить `1e308` в логике — только в данных барьеров.
- Не начинать новую часть, не отчитавшись по предыдущей.
- Не допускать `Infinity` как игровое состояние.
- Не переписывать ТЗ молча — только с явным перечислением изменений.
- Не пытаться проектировать Ярус 3+ — по договорённости горизонт: **Ярус 1 (20 механик) + Ярус 2 (10 механик)**.
